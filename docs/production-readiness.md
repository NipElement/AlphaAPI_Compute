## 1. 六维结论(每维一段,原文)

### 硬件拉起(hardware-bringup)

The control-plane rehearsal is genuinely strong — onboarding, ownership state machine, admission gates and queues are tested paths that transfer — but everything between power-on and that control plane existing is unwritten: no cluster bootstrap, a dgx overlay that renders zero workloads, no way to move an image onto a real node, no GPU/IB/storage manifests, a completion gate that asserts the GPUs must NOT exist, and open decisions (control-plane placement, NVMe layout, fabric management, driver ownership) that block the pre-writing the prime directive demands; the honest distance is that roughly the lower half of the stack does not exist yet, though most of it is pre-buildable this week. Day-0 runbook skeleton (R = pre-buildable/rehearsable on this EC2 now): 1) rack/power/BMC access + firmware inventory vs written baseline (R: checklist/script); 2) DGX OS validation, NVMe layout, nvidia-smi + field diag per node (R: scripts only); 3) fabric bring-up — cabling plan, switch/subnet-manager config, ibstat link-rate checks (blocked on fabric DECISION; R: check scripts); 4) admin/control-plane host up (blocked on placement DECISION), containerd + kubeadm init from pre-written ClusterConfiguration reusing POD_CIDR/SERVICE_CIDR, vendored CNI applied, 4 nodes joined (R: every manifest and script); 5) private registry up, digest-pinned image set mirrored and verified (R: fully rehearsable via kind+local-registry pattern); 6) `make deploy-dgx` — completed dgx overlay + vendored Volcano + monitoring + storage classes (R: fully rehearsable as a dgx-sim overlay on the kind cluster); 7) GPU Operator with the decided driver flags → nvidia.com/gpu=8 per node, DCGM scraping and alerts live (R: values + helm template render); 8) Network Operator + RDMA resources → NCCL 2-node all-reduce and single-node NVLink bandwidth meet the contractually written thresholds (R: vcjob manifests + thresholds); 9) NVMe storage classes live, fio baseline recorded, real sanitize path timed (partially R after the storage decision); 10) `onboard-node.sh gpu dgx01..04` — the one step already rehearsed on every matrix run (NODE-01); 11) verify-dgx.sh completion gate + KUBE_CONTEXT-parameterized smoke matrix against the real cluster (R: build and dry-run now); 12) TLS-terminated ingress + seeded credentials replaced before any external exposure; 13) HW-01..15 acceptance matrix executed and evidenced; 14) end-to-end DIRECT-reservation dry run before the first paying customer. Steps 4-8 and 11 are the pre-build backlog; steps 5, 6 and 11 can be rehearsed to completion on this machine before the hardware ships.

### 公网暴露(public-exposure)

In this dimension the platform is honest but essentially at zero: the entire public path — TLS, certificates, ingress, DNS, DDoS posture, even a production deployment of the gateway itself — exists only as comments promising "the real machines will have it", and the dgx overlay ships no serving workload at all. The gateway is a competent prelab aggregator but a dev-server-grade public listener: unbounded thread-per-connection with no timeouts, default admin passwords live in the rehearsed config, unthrottled 120k-iteration logins, and all users/sessions in one process's memory, which also forbids HA. The good news is that roughly three quarters of the distance is closable on the EC2 today (edge manifests rehearsed in kind, server hardening, fail-closed secrets, throttling, persistent/stateless sessions, logging, cookie/CSRF fixes are all S/M efforts), but two business decisions — the customer identity provider and the edge/domain/DDoS topology — gate the rest and are not yet owned by anyone; until they land, the day-0 cutover cannot even be scripted, and launch speed will be set by whichever decision is made last.

### 客户产品链(tenant-product)

The control plane underneath is genuinely rehearsed, but the paying customer's path itself does not exist yet: every link a customer would personally touch is either missing or dead-ends. Onboarding tenant #3 requires coordinated edits to roughly twelve hardcoded lists (one of which — the platform-ingress fence's enumerated NotIn — fails open for an unlisted tenant); a rented dev machine is a sleep-loop pod with no SSH, exec, or tunnel and a 20KB log tail as the product's entire I/O surface; there is one frozen CPU image and no registry; results can never leave the cluster; the inference product creates endpoints nothing can connect to; and the per-minute price on the offer page has zero metering, ledger, or billing code behind it, with every candidate data source volatile. The good news for the prime directive: seven of nine gaps are fully pre-buildable and rehearsable on this EC2 today in kind — the true blocker to start this week is a single business decision (which owner pool serves on-demand customers and at what isolation granularity), because the onboarding automation, admission-policy generalization, and metering ledger all take shape around that answer.

### 计费计量(billing-metering)

In the billing and metering dimension the distance to a paid public launch is total: the repo contains not one line of code, config, or test that measures, prices, records, or invoices anything — no per-tenant usage series exists or is derivable (three fleet-level scrape jobs, no kube-state-metrics/cAdvisor), the only time-series store is 3-day emptyDir Prometheus that the repo itself correctly refuses to treat as a source of truth, the offer-page prices appear nowhere in the system, the only contract model is the VAST marketplace mock (customer dedicated rentals have no record of customer, term, price, or renewal), and there is no suspension lever for a non-paying tenant. The mitigating fact is that nearly all of it is EC2-NOW pre-buildable within the house rules: the codebase already has every ingredient the minimal honest skeleton needs — a proven stdlib watch/reconcile pattern, an idempotency discipline (transitionId/OWN-04) that maps directly onto exactly-once usage intervals, a hash-evidence habit for a tamper-evident ledger, Retain-class PVCs to hold it, VAP admission gates to enforce suspension, and a 34-case test matrix to bolt MTR/BIL/SUS cases onto. One metering service (sole writer of an append-only, hash-chained allocation ledger keyed on pod UID, exporting per-tenant gauges for Prometheus cross-check), a versioned price book, a deterministic invoicer, a RentalAgreement record wired into the DIRECT flow, and a rehearsed freeze runbook constitute roughly two to three weeks of focused work — but the last mile is gated by one genuinely un-codeable decision (merchant of record, payment rails, prepaid vs postpaid, and the tenant billing-class mapping) that should be made now, because the metering schema depends on it.

### 可靠性运维(reliability-ops)

The control-plane logic itself is in unusually good shape for a prelab (durable transition state in a ConfigMap, idempotent transitionIds, readback recovery, drift correction — all matrix-tested), but everything AROUND it that a paid service stands on does not exist yet: the production (dgx) overlay ships zero workloads and the deploy path is kind-load/docker-cp lab-isms; there is no head-node plan, so on 4 sellable DGX nodes there is literally nowhere designed for the API server, etcd, gateway or Prometheus to live; nothing is backed up (no etcd snapshot, no velero, monitoring on emptyDir, users/sessions in process memory); alerts terminate in a null receiver and there is no node-down, disk-full or GPU-fault detection path for real hardware; customer data durability on local NVMe is an unmade decision already contradicted by the offer page (30TB included, Retain-class semantics local-path cannot honor); upgrade means teardown+rebuild and there is no maintenance state in the ownership machine; and only 6 runbooks exist, none of them incident runbooks. Real distance to launch in this dimension: roughly 5 large pre-buildable work packages (production overlay + registry, backup/restore, alerting/paging + fleet-health coverage, upgrade/maintenance procedure, incident runbooks + chaos rehearsal) all doable on EC2 now, two hardware-day items that can be pre-written (DCGM/Xid pipeline, Loki), and three business decisions (head-node hardware, identity provider, storage durability SLA) that block everything downstream of them and should be forced this week.

### 上线安全(security-launch)

The internal posture genuinely earned its rehearsal value — least-privilege RBAC split, PSA restricted tenants, CEL admission gates, empirically-probed NetworkPolicies, digest-pinned upstream images, and two real audits with confirmed fixes — but every one of those controls assumes the perimeter is a trusted 127.0.0.1 port-forward, and nothing that faces the internet exists yet: default passwords are the live credentials with no Secret machinery in the repo, there is no TLS or ingress artifact of any kind, login is unthrottled brute-forceable CPU amplification with no password-change path, the audit trail dies with the pod, and the overlay that actually ships to hardware has drifted so far from the rehearsed one that it would deny the paid DIRECT product's own workloads while omitting the queue-entitlement gate. The honest distance is roughly: four P0 build items that are fully pre-buildable and rehearsable on this EC2 today (secrets + fail-closed defaults, TLS front, overlay policy unification, CIDR parameterization), one P0 runbook (host/BMC hardening) that can be written before hardware, and three owner decisions that gate the rest — IdP vs hardened built-in auth, image registry, and the sub-node co-tenancy/isolation-disclosure question that the "NVLink guaranteed in writing" offer makes contractual. None of this requires the machines; all of it stops being schedule-compatible with "as fast as possible" if it is still open on delivery day.

## 3. DGX Day-0 runbook 骨架(硬件维给出的 14 步,R=现在可预建/排练)

Day-0 runbook skeleton (R = pre-buildable/rehearsable on this EC2 now): 1) rack/power/BMC access + firmware inventory vs written baseline (R: checklist/script); 2) DGX OS validation, NVMe layout, nvidia-smi + field diag per node (R: scripts only); 3) fabric bring-up — cabling plan, switch/subnet-manager config, ibstat link-rate checks (blocked on fabric DECISION; R: check scripts); 4) admin/control-plane host up (blocked on placement DECISION), containerd + kubeadm init from pre-written ClusterConfiguration reusing POD_CIDR/SERVICE_CIDR, vendored CNI applied, 4 nodes joined (R: every manifest and script); 5) private registry up, digest-pinned image set mirrored and verified (R: fully rehearsable via kind+local-registry pattern); 6) `make deploy-dgx` — completed dgx overlay + vendored Volcano + monitoring + storage classes (R: fully rehearsable as a dgx-sim overlay on the kind cluster); 7) GPU Operator with the decided driver flags → nvidia.com/gpu=8 per node, DCGM scraping and alerts live (R: values + helm template render); 8) Network Operator + RDMA resources → NCCL 2-node all-reduce and single-node NVLink bandwidth meet the contractually written thresholds (R: vcjob manifests + thresholds); 9) NVMe storage classes live, fio baseline recorded, real sanitize path timed (partially R after the storage decision); 10) `onboard-node.sh gpu dgx01..04` — the one step already rehearsed on every matrix run (NODE-01); 11) verify-dgx.sh completion gate + KUBE_CONTEXT-parameterized smoke matrix against the real cluster (R: build and dry-run now); 12) TLS-terminated ingress + seeded credentials replaced before any external exposure; 13) HW-01..15 acceptance matrix executed and evidenced; 14) end-to-end DIRECT-reservation dry run before the first paying customer. Steps 4-8 and 11 are the pre-build backlog; steps 5, 6 and 11 can be rehearsed to completion on this machine before the hardware ships.
