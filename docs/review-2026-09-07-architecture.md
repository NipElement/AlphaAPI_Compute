## 已修复的缺陷

| 发现 | 修复与验证 |
|---|---|
| 登录和改密时在全局身份锁内执行 PBKDF2，拖住已登录用户的请求 | 哈希在锁外执行，签发会话或写入新密码前重新核对身份版本。真实 HTTP 并发测试验证会话读取不被阻塞，账号删除重建期间不能签发或覆盖新身份。 |
| 清理撤销记录时，即使内容没变也重复提交 SQLite | 仅在内容变化时写入；保留撤销的持久性，并验证无变化不增加数据库写入。 |
| 实例查询把 403 / 500 等上游错误显示成“没有实例” | 只有真正的 404 才返回空列表，其余错误保留给调用方。 |
| 机群读取所有权 CR 失败后继续生成零合同信息；告警/事件失败则返回无异常的空列表 | 所有权读取失败直接报错；告警和事件作为可选数据独立记录 errors，机群操作仍可用。概览显示不可用而非零告警，审计页显示读取失败。 |
| 机群 CPU / 内存统计只读取模拟资源，上真集群后会显示零 | 按 GPU 资源配置选择 lab 或原生资源，将 CPU、内存统一为 vCPU、GiB。接口删除 simVcpu* / simMem* 字段，前后端统一使用 vcpuTotal/Used、memGiTotal/Used；基础设施表格同步修改。包含普通 init container 的资源峰值。 |
| 计量将无单位的原生 memory 字节数当成 GiB | 原生内存复用字节到 GiB 的转换，只有 lab 扩展资源直接计 GiB。回归覆盖 Gi/Mi、无单位字节数、科学计数法和模拟整数。原生无后缀内存使用字节的定义见 [Kubernetes 资源文档](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#meaning-of-memory)。 |
| 翻译改为模块导入后，L0 还在用旧的 eval 方式解析，导致检查失败 | 翻译改为前端直接消费的两个 JSON；Python 检查 key 对齐、重复键和非法值，新增检查器自身的成功/失败测试。 |
| 网关安全测试只检查 do_* 首行源码，阻碍安全的入口合并 | 改为真实 HTTP/1.1 连续请求：先消费登录 body，再在同一连接上发送匿名/跨源请求，验证拒绝且关闭带未读 body 的连接。 |

## 结构与冗余清理

- 控制器 reconcile 从 **763 行降到 227 行**。共享安全门在分派前执行，ARISE、VAST、DIRECT、MAINTENANCE 各自处理状态流转，统一开始排空和超时处理。保留合同门、PDB、卷残留阻断、清理与健康检查；没有通过删掉安全分支缩短代码。整个控制器仍约 1,760 行，文件交付方式未变化，改善主要是职责与重复逻辑。
- ResourceWorkspace 从 **1,346 行降到 641 行**；ResourceCreateDrawer 独立拥有表单、校验、创建状态和相关样式。列表、筛选与详情仍由工作台管理，四类工作负载共享一份元数据。创建实现从原组件移走，未保留第二份。
- Arco 控件规则统一到 controls.css；global.css 保留主题变量和应用布局。移除已被替换的卡片、分页、进度条及页面中残留的分页样式，消除确认已被后续同选择器覆盖的声明。
- 删除每种语言 **83 条确认无引用的旧文案**，词库从 490 减为 407 个 key；合并并删除旧的 TS 词库及 console.ts。动态状态、工作负载元数据等实际引用均保留。
- POST / PUT / DELETE 复用统一的请求初始化、CSRF、认证和代理入口。删除确认未使用的 Python import；TypeScript 继续启用 noUnusedLocals / noUnusedParameters。
- 新增 **make check**，复用既有 L0 和前端构建入口，避免只验后端就把整个平台当成已验证。它会按锁文件安装前端依赖，需要缓存或网络；不部署服务。
- README、gaps 和认证代码说明同步当前 SQLite 单写入者模型，去掉已经不成立的服务数量和恢复能力表述。带日期的旧验收记录保留，当前说明明确链接其后续结论。

## 性能实测

用同一份合成的单租户已关闭区间测量 usage_summary：10,000 条原为 0.176 秒，100,000 条原为 1.770 秒。剖析显示主要开销在重复的 strptime / locale 解析。改用标准库 ISO 解析器，并明确拒绝缺失 UTC 时区、无效日期和不符合账本格式的时间后，同样输入分别为 **0.026 秒、0.263 秒**，100,000 条约快 **6.7 倍**，区间总量和用量不变。

这是共享开发机上的函数基准，不是线上并发或计费吞吐承诺。查询仍扫描账本，账本仍常驻内存；减少时间解析成本没有把 O(n) 变成 O(1)。长期运营或更多租户需要有索引的查询存储、汇总和归档边界，不能靠继续叠加内存缓存掩盖增长。

## 保留的架构边界

当前 gateway（身份/代理）、portal（租户资源）、ops（期望状态）、controller（节点所有权）、metering（占用账本）、备份和 SSH 接入的边界有明确用途，尤其对应不同 Kubernetes 权限。将这些服务合成一个有所有权限的大进程，会扩大故障与越权范围。当前优先清理的是隐藏状态、吞错和职责混杂，标准库实现仍适合这些有限职责。

账本写入、独立账单核验和备份回读保留各自验证路径；测试夹具及已封存证据也保留。它们用于发现运行实现的错误，不是可以按“看起来重复”随便删除的运行时代码。

## 仍然存在的边界

- 这是针对当前单控制面、小规模 GPU 机群的实现。SQLite 明确单写入者；网关与本地账本不是直接增加副本即可获得高可用。需要 HA 时应单独设计状态迁移与一致性。
- 用量查询与历史校验还有随账本增长的开销；审计页当前展示控制器事件，不等于长期合规审计仓库。详细用量接口最多返回最近 500 条，完整历史仍从账本核验。
- 当前产品表单生成的工作负载及普通 init container 已覆盖；任意外部注入的 restartable sidecar、Pod 级资源等新模型需要连同准入、调度和计量一起验证，不能只改一个统计函数。
- 生产存储硬限制、异机恢复、真实公网 TLS/SSH 信任、持续并发与真实 GPU/NVLink/NCCL/RDMA 仍按既有上线条件验收。Chromium 检查不能表述成 Safari/Firefox 全覆盖。当前功能和模拟集群的测试通过，也不等于这些生产条件已经通过。
